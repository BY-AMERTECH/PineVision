# PineVision — Drone-to-Laptop Video Pipeline Investigation

**Scope:** Read-only code analysis of the live RTMP/HLS stream path and the uploaded-MP4 path, covering connection, playback, detection, tracking, counting, and classification. No project files were modified, created, deleted, renamed, or reformatted at any point in this analysis.

**Method / limitation up front:** All findings below come from static code tracing across the full backend (`backend/app.py`, `backend/drone_conn/*.py`) and frontend (`frontend/js/*.js`, `frontend/pages/client/drone-view.html`) source, plus the project's own `FIXES_NEEDED.md` and `DETECTION_TESTING_PLAN.md` docs, cross-checked line-by-line against current code. No `device_bash` tool was available in this session, so nothing was actually executed: no Flask server was started, no MediaMTX instance was run, no RTMP stream was pushed, and no MP4 file was uploaded through the live UI. Every conclusion is either (a) **confirmed by code tracing** — meaning the code path is deterministic and the outcome follows directly from reading it — or (b) **flagged as requiring runtime verification**, and labeled as such.

---

## 1. Overall Status

The drone-to-laptop pipeline is architecturally intact and most previously-documented bugs in `FIXES_NEEDED.md` have already been fixed in the current codebase. However, code tracing surfaced two categories of problems the project's own documentation does not mention:

- A **confirmed data-integrity bug**: ending a video (MP4) scan while it is still analyzing overwrites a correct "failed" scan record with an incorrect "completed" record that promises a detection manifest which was never written to disk.
- A **confirmed double-counting bug**: the per-category duplicate-prevention logic in `detect_frame()` does not prevent the same tracked object from being counted in two different classification categories if its detected class label changes between frames.

Separately, `DETECTION_TESTING_PLAN.md` documents a batch of tracking/counting fixes ("Fix 1" through "Fix 7") as already implemented — none of these exist in the current code. This is a significant documentation-vs-reality gap that could mislead anyone relying on that document to understand the current state of the tracker.

The live-stream (RTMP → MediaMTX → HLS) connection path and the MP4 upload/manifest path are both structurally sound and should function under normal single-scan usage, based on code tracing. Live drone hardware, a live RTMP feed, and a running MediaMTX instance were not available to this session, so end-to-end runtime playback was not verified.

## 2. End-to-End Architecture Map

**Live stream path:**
`DJI Fly (or ffmpeg test source)` → RTMP `rtmp://<host>:1935/pinevision_scan` → `mediamtx.exe` (config: `mediamtx/mediamtx.yml`, managed by `backend/drone_conn/process_manager.py::ensure_running()`) → MediaMTX re-exposes the stream as HLS (`http://<host>:8888/pinevision_scan/index.m3u8`) and RTSP (`rtsp://<host>:8554/pinevision_scan`) → frontend `hls.js` plays the HLS URL in `<video id="drone-feed">` (`frontend/js/drone-view.js::loadHlsStream()`) → backend `backend/drone_conn/stream_capture.py::HLSStreamCapture` independently opens the **RTSP** URL (preferred over HLS, with automatic fallback to HLS) via OpenCV to pull frames for detection → `backend/drone_conn/detection.py::PineappleDetector._detection_loop()` runs YOLOv8 + DeepSORT on those frames → results written to Firestore (`scans` and `blocks` collections) via `backend/drone_conn/firebase_client.py` → frontend listens with Firestore `onSnapshot` for live stat updates.

**Uploaded-MP4 path ("two-phase" design):**
User selects an MP4 in `drone-view.html` → `drone-view.js::handleFileSelect()` loads the file locally into the `<video>` element via `URL.createObjectURL()` (paused, not yet playing) and simultaneously `POST /api/drone/upload-video` (multipart) → `backend/drone_conn/routes.py::upload_video()` saves the file to `%TEMP%/pinevision_uploads/` and calls `PineappleDetector.start_video_scan()` → a background thread runs `_video_scan_loop_sequential()`, which reads the video frame-by-frame with OpenCV (independent of anything the browser is doing), runs YOLO+DeepSORT on every Nth frame, and accumulates an in-memory manifest of timestamped bounding boxes → periodic partial progress is written to Firestore (`scanProgress`, `processedFrames`, `totalFrames`) → when the whole file has been read, the full manifest is written to disk as JSON (`save_detection_manifest()`) and only then is the Firestore scan document marked `status: 'completed'`, `manifestReady: true` → the frontend's Firestore listener (`startScanCompletionListener()`) detects `manifestReady` and fetches `GET /api/drone/scan/<scan_id>/manifest` → loads all boxes into `BboxOverlay`, then starts local 1× playback of the already-loaded video with boxes drawn per `video.currentTime`. Detection speed never affects playback speed — the two are fully decoupled by design.

**Key backend files/functions:**
- `backend/app.py` — Flask entry point; registers `drone_bp`; pre-warms the YOLO model on the single reloader-main process (`__main__` block, guarded by `WERKZEUG_RUN_MAIN`).
- `backend/drone_conn/routes.py` — all `/api/drone/*` endpoints (`prepare`, `connect`, `status`, `start-detection`, `stop-detection`, `upload-video`, `scan/<id>/manifest`, `video-time`).
- `backend/drone_conn/service.py` — RTMP URL validation + MediaMTX path lookup for `/connect` and `/status`.
- `backend/drone_conn/process_manager.py` — auto-launches `mediamtx.exe` if its control API isn't already reachable.
- `backend/drone_conn/network.py` — local IPv4 detection for pre-filling the RTMP URL shown to the user.
- `backend/drone_conn/stream_capture.py` — `HLSStreamCapture`, the OpenCV-based frame puller for the live path (RTSP-preferred, auto-reconnect).
- `backend/drone_conn/detection.py` — `PineappleDetector`: model loading, DeepSORT tracking, classification, both scan loops, Firestore write orchestration.
- `backend/drone_conn/firebase_client.py` — all Firestore reads/writes (`create_scan_session`, `update_detection_batch`, `complete_scan_session`, `save_detection_manifest`, alert helpers).

**Key frontend files:**
- `frontend/pages/client/drone-view.html` — page markup (video element, canvas overlay, modals, stats panel).
- `frontend/js/drone-view.js` — all drone-view page logic: connect workflow, HLS playback, detection start/stop, upload workflow, manifest fetch/playback, stream-loss handling, end-scan workflow.
- `frontend/js/app.js` — shared app shell (topbar, sidebar, page-transition link interception, `window.initPage()` dispatch).
- `frontend/js/scans.js` — scan history page, reads directly from Firestore `scans` collection.

## 3. Connection and Playback Findings

**RTMP → MediaMTX → HLS handoff:** Confirmed sound by code tracing. `service.py::connect()` validates the RTMP URL with a regex, queries MediaMTX's control API (`mediamtx.py::get_path()`), and only returns a `hls_url` if MediaMTX reports the path as `ready` (i.e., a publisher is actively streaming). If MediaMTX itself isn't reachable, `process_manager.py::ensure_running()` auto-launches it from `mediamtx/mediamtx.exe` before the user even gets to the Connect modal (`routes.py::prepare()`, called on `show.bs.modal` in `drone-view.js::autoPrepareModal()`). A genuine HLS playlist and two-plus minutes of recorded `.ts` segments already exist on disk at `output/index.m3u8` — direct evidence that this pipeline has produced a real, valid HLS stream from a prior run.

**Frontend live playback:** `drone-view.js::loadHlsStream()` uses `hls.js` when supported, with a native-`<video>` fallback for Safari-class browsers. `HLS_CONFIG` sets reasonably tight timeouts (8s manifest/level load, 2 retries). Fatal `hls.js` errors and native `<video>` `error` events both route to `onHlsFatalError()`, which either shows a connect-failure message (first connect) or triggers `handleStreamLost()` (post-connect drop). This looks correct.

**Backend live frame capture:** `stream_capture.py::HLSStreamCapture` does **not** consume the same HLS URL the browser plays — it derives an RTSP URL from the HLS URL (`http://HOST:8888/PATH/index.m3u8` → `rtsp://HOST:8554/PATH`) and prefers RTSP for capture, falling back to HLS only if RTSP fails to open. This is a reasonable design (RTSP avoids HLS segment-boundary read stalls) but means the browser and the backend are technically consuming two different transport protocols from the same MediaMTX source — worth knowing when debugging "video plays fine but no detections happen," since a firewall or MediaMTX config blocking RTSP specifically (port 8554) would silently degrade to HLS-based capture rather than fail outright (the fallback is silent besides a log line).

**Reconnect logic:** `drone-view.js::startStatusPolling()` polls `/api/drone/status` every 5s while `active`/`reconnecting`; three consecutive failures (`MAX_RECONNECT = 3`, i.e. ~15s) trigger `handleStreamLost()` → `stopDetection()` → transition to `failed`. This is now correctly `await`-ed (see Section 4, issue #5 status). Independently, `stream_capture.py`'s own capture loop has its own reconnect logic (up to `_MAX_RECONNECTS = 5` internal reconnects before giving up) — these two reconnect mechanisms (frontend polling vs. backend capture thread) are independent and not coordinated; a stream that recovers on the backend side within `stream_capture.py`'s window but stays down for longer than the frontend's 15s poll window would still surface as "Stream lost" to the user even if the backend eventually reconnects. This is a design characteristic, not confirmed as a bug, but is worth runtime verification if intermittent "stream lost" reports occur despite a technically-recovering feed.

**MP4 upload/playback:** The two-phase design is real and consistently implemented across `routes.py::upload_video()`, `detection.py::_video_scan_loop_sequential()`, `firebase_client.py::save_detection_manifest()`/`complete_scan_session()`, and `drone-view.js::loadManifestAndPlay()`/`startVideoPlayback()`. The manifest is always written to disk before Firestore is told `manifestReady: true` (explicit code comment and ordering confirm this at `detection.py` lines 1022–1060), so a race where the frontend fetches the manifest before it exists is not possible **for the normal completion path**. See Section 5, Issue A for the abnormal (user-initiated interruption) path, where this guarantee does not hold.

## 4. Detection / Counting / Classification Findings

**Model loading:** `PineappleDetector.__init__()` (`detection.py` ~lines 177–240) loads a custom-trained model from `backend/best.pt` (confirmed present on disk, ~22.5 MB) via `ultralytics.YOLO`, with a `torch.hub`/YOLOv5 fallback if `ultralytics` import fails. A single `DeepSort(max_age=30, n_init=3, max_iou_distance=0.7)` tracker instance and a single `unique_ids` dict of three sets (`bearing`, `non_bearing`, `non_viable`) are created as **instance attributes of the detector**, not per-scan objects.

**Per-frame pipeline (`detect_frame()`, lines 275–369):** Frame is downscaled to a fixed inference size if larger; YOLO runs with no explicit confidence or IoU/NMS threshold override (uses ultralytics defaults); results are converted to `(bbox, confidence, class_name)` tuples and passed to `DeepSort.update_tracks()`. Only `is_confirmed()` tracks are counted. Each confirmed track's `class_name` (read from `track.det_class`, which DeepSORT sets from the most recently matched detection for that track) is normalized into one of `bearing` / `non_bearing` / `non_viable`, then checked against `self.unique_ids[category]` and added if not already present.

**Confirmed bug — cross-category double counting (HIGH severity):** The duplicate check at `detection.py` lines 362–363 (`if track_id not in self.unique_ids[category]: self.unique_ids[category].add(track_id)`) only checks membership **within the one category being classified this frame** — it never checks the other two sets. Because `track.det_class` reflects the classifier's output for the *most recent* matched detection, and YOLO classification confidence for a borderline pineapple can plausibly flip between adjacent classes across frames (e.g., "non_bearing" in frame N, "bearing" in frame N+5), the same physical `track_id` can be legitimately absent from one category's set and present in another's, and would then be added to *both*. The result: `total_count = len(bearing) + len(non_bearing) + len(non_viable)` can overcount the true number of distinct plants, and a single pineapple can contribute to two different percentage buckets simultaneously. This affects **both** the live-stream and MP4 pipelines equally, since both call the same `detect_frame()`. This is a confirmed logic defect from code tracing; the actual overcount rate would depend on how often the classifier flips per track and can only be quantified with a real video (runtime verification needed for magnitude, not for existence of the defect).

**Documentation mismatch (confirmed):** `DETECTION_TESTING_PLAN.md` claims five fixes are already implemented in this codebase: `_init_tracker()`/parametrized `reset_tracking(frame_skip, live_fps)` (Fix 1), `advance_kalman_only()` for Kalman-only updates on skipped frames (Fix 2), explicit `iou=0.45` NMS (Fix 3), a corrected `should_detect` frame-index formula (Fix 5), and queue-lag/dropped-frame logging (Fix 7). None of these exist in the current code:
- `reset_tracking()` (`detection.py` lines 241–257) takes **no parameters** and hardcodes `DeepSort(max_age=30, n_init=3, max_iou_distance=0.7)` — there is no `_init_tracker()` function anywhere in the file.
- There is no `advance_kalman_only` anywhere in `detection.py` or `stream_capture.py` (grep returned zero matches).
- `self.model(inference_frame, verbose=False)` at line 301 passes no `iou` argument.
- The video-scan frame-skip check is the plain `if frame_count % process_every_n_frames != 0: continue` (line 917) — not the claimed `(frame_index == 1) or ((frame_index-1) % frame_skip == 0)` formula.
- The log markers the plan says to watch for (`🔧 Tracker init`, `⚠️ [LAG]`, `⚠️ [SLOW]`) do not exist anywhere in `drone_conn/` (grep confirmed).

This means the tracker-tuning and dedup work described as "this batch" in that document was either never actually merged, or was reverted/lost. Anyone consulting `DETECTION_TESTING_PLAN.md` to understand current tracking behavior would be working from an inaccurate picture of the code.

**Confirmed bug — `upload-video` discards the frontend's `frame_skip` (MEDIUM severity):** `routes.py::upload_video()` (lines 253, 284) parses `frame_skip` from the multipart form but then calls `start_video_scan(..., process_every_n_frames=5, ...)` with a hardcoded `5`, never passing the parsed variable through. In practice this is low-impact today because `drone-view.js::apiUploadVideo()`'s `FormData` (lines 663–666) never appends a `frame_skip` field in the first place, so the frontend isn't actually trying to control this value — but the backend parsing code creates a false impression that it's configurable, and if a future frontend change starts sending `frame_skip`, it will silently have no effect.

**Confirmed dead code:** `push_video_time()` (`detection.py` lines 259–268) is a no-op stub — `POST /api/drone/video-time` (`routes.py` lines 331–356) still exists and returns `{'ok': True}`, but calling it does nothing. `_video_scan_loop()` (the older, non-sequential MP4 loop, lines 700–840) is defined but never invoked anywhere — `start_video_scan()` always spawns `_video_scan_loop_sequential()` instead. Neither is currently harmful (both are simply unused), but both represent maintenance risk if someone edits the wrong one expecting it to take effect.

**Global singleton state (confirmed architectural limitation, matches the project's own "Remaining Issues" list in `DETECTION_TESTING_PLAN.md`):** `self.tracker`, `self.unique_ids`, `self.detection_active`, `self.detection_thread`, and `self._current_scan_id` are all single instance attributes on the one `_detector` singleton returned by `get_detector()` (module-level global, lines ~1273–1296). There is no per-scan isolation. `start_video_scan()` calls `self.reset_tracking()` unconditionally (line 686) without first checking `self.detection_active` — so starting a second scan (live or MP4) while one is already running will silently wipe the in-progress scan's tracker state and unique-ID counts out from under it, corrupting whichever scan was already active. The UI's button visibility (`toggleEl('btn-connect', isInactive)` / `toggleEl('btn-upload-video', isInactive)` in `renderUI()`) makes this hard to trigger through normal single-tab use, since Connect/Upload are hidden once a session is active — but nothing in the backend itself prevents two concurrent requests (e.g., two browser tabs, or a stale request retried after a timeout) from both reaching `start_detection()`/`start_video_scan()`.

## 5. Confirmed Issues

### Issue A — Ending a video scan mid-analysis corrupts the scan's final status (HIGH severity)
- **Files/functions:** `frontend/js/drone-view.js::handleEndScan()` (lines 1045–1055), `backend/drone_conn/routes.py::stop_detection()` (lines 187–227), `backend/drone_conn/detection.py::PineappleDetector.stop_detection()` (lines 566–654) and `_video_scan_loop_sequential()` (lines 908–1002).
- **Expected behavior:** Clicking "End Scan" while an uploaded MP4 is still being analyzed should cleanly abort the background analysis and leave the scan record in an unambiguous, correct final state (e.g., `status: 'failed'` or `status: 'cancelled'`, no dangling promise of a manifest).
- **Actual behavior (confirmed by tracing):** `handleEndScan()` calls `stopDetection()` **unconditionally**, regardless of `DRONE_STATE.videoMode` — there is no branch that treats an in-progress video scan differently from a live stream. This calls `POST /api/drone/stop-detection`, which calls the generic `PineappleDetector.stop_detection(block_id, scan_id, user_id)`. That function sets `self.detection_active = False` and joins the background thread (`self.detection_thread.join(timeout=5.0)`). Because `_video_scan_loop_sequential()`'s main loop condition is `while self.detection_active:` (line 909), the background thread exits on its next iteration, takes its `finally` branch (`self._current_scan_id = None`, `self.detection_active = False`), and — since `success_flag` was never set to `True` (that only happens on natural end-of-file) — correctly writes `status: 'failed'`, `error: 'Analysis was interrupted before completion.'` to the scan document (lines 990–1002), **without** ever writing a manifest file. The `join()` call in `stop_detection()` waits for exactly this to finish. Then `stop_detection()` proceeds anyway, unconditionally reads the (now-frozen, partial) `self.unique_ids` counts and calls `complete_scan_session()` (line 613), which sets `status: 'completed'` and `manifestReady: true` on the *same* scan document — **overwriting** the correct `'failed'` status the background thread had just written, with counts that reflect only the frames processed before interruption, and a `manifestReady: true` flag pointing at a manifest file that was never created (the temp video file was already deleted at this point too, per lines 984–985).
- **User-visible impact:** In the common case, this has no immediately visible effect, because `handleEndScan()` also calls `stopFirebaseListener()` (line 1069) and transitions the UI to `idle`/navigates away around the same time, so the corrupted write typically lands after the frontend has already stopped listening. The impact is **silent data corruption in Firestore**: the scan's history record will show as `completed` with `manifestReady: true` even though no manifest exists, which would surface as a 404 (`manifest_not_found`, `routes.py` line 317-319) if anything ever tries to re-fetch that scan's manifest later (e.g., a "re-view this scan" feature, or a support/debug tool), and the scan's reported bearing/non-bearing/non-viable percentages in `scans.js`'s history list would reflect an artificially early, partial cutoff of the video rather than a real "failed" scan.
- **Root cause:** `stop_detection()` is a single function written for the live-stream pipeline's semantics and is reused as-is for the video pipeline's "End Scan" action, without checking whether the scan already reached a terminal state on its own, or whether `DRONE_STATE.videoMode` should route to a different backend action (e.g., an abort endpoint that does not call `complete_scan_session()` on top of an already-'failed' scan).

### Issue B — Cross-category double counting in `detect_frame()` (HIGH severity)
- **Files/functions:** `backend/drone_conn/detection.py::PineappleDetector.detect_frame()`, lines 341–369, specifically the per-category duplicate check at lines 362–363.
- **Expected behavior:** Each physically distinct pineapple (tracked object) should be counted exactly once, in exactly one category, for the lifetime of a scan.
- **Actual behavior (confirmed by tracing):** `self.unique_ids` is three independent sets, one per category. The membership check `if track_id not in self.unique_ids[category]` only looks at the set for the category assigned to the track *this frame*. If the same `track_id`'s classified category (`track.det_class`, which DeepSORT updates from the most recent matched detection) changes between frames — plausible for a plant whose visual features put it near a decision boundary between "bearing" and "non-bearing," for instance — that `track_id` will be added to more than one category's set, since it was never checked against the *other* two sets.
- **User-visible impact:** Inflated total pineapple counts and inflated/inaccurate percentage splits shown in the stats panel, end-of-scan modal, and scan history, in any video where at least one tracked plant's classification is not perfectly stable across frames. The size of this effect (how often it actually happens in real footage) cannot be determined without running real detection on a real video — that magnitude question is a runtime-verification item (Section 6).
- **Root cause:** Duplicate prevention was designed per-category (three independent sets) rather than globally per-track (one global set mapping `track_id → category`, or at minimum a global "already-counted" set checked before any per-category add).

### Issue C — `upload-video` silently ignores the `frame_skip` form field it parses (MEDIUM severity)
- **Files/functions:** `backend/drone_conn/routes.py::upload_video()`, lines 250–286 (parses `frame_skip` at line 253, discards it and hardcodes `process_every_n_frames=5` at line 284).
- **Expected/actual:** The parsed value is computed and then never used. Currently harmless because the frontend never sends this field (`drone-view.js::handleFileSelect()`, lines 663–666, only appends `file`, `block_id`, `user_id`), but it is a latent trap for any future change that assumes this parameter is wired up.
- **Impact:** None today; becomes a real "my setting is being ignored" bug the moment any caller starts sending `frame_skip`.

### Issue D — No concurrent-scan protection on the shared detector singleton (MEDIUM severity)
- **Files/functions:** `backend/drone_conn/detection.py::get_detector()` (module-level singleton, ~lines 1273–1296); `start_video_scan()` line 686 (`self.reset_tracking()` called unconditionally, no check of `self.detection_active`); `start_detection()`/`_detection_loop()` (live path) share the same `self.tracker`/`self.unique_ids`/`self.detection_active` instance attributes.
- **Expected/actual:** A second scan (live or MP4) started while one is already active will reset the shared tracker and unique-ID sets, corrupting the in-progress scan's counts, rather than being rejected or queued.
- **Impact:** Not reachable through the normal single-session UI (Connect/Upload buttons are hidden once a scan is active, per `renderUI()`), but reachable via multiple browser tabs, a stale/duplicated network request, or any future multi-scan feature. This is the same limitation the project's own `DETECTION_TESTING_PLAN.md` names under "Remaining Issues" (#1 and #5) as still outstanding, and code tracing confirms it is indeed still outstanding.

### Issue E — `FIXES_NEEDED.md` is stale (all 7 listed issues are already fixed) (INFORMATIONAL)
- Cross-checking each item in the project's own `FIXES_NEEDED.md` against current code:
  - **#1 (double `initPage()` call, `drone-view.js`):** Fixed. No `document.addEventListener('DOMContentLoaded', initPage)` exists anywhere in the current `drone-view.js` (confirmed via full read and a targeted grep, zero matches). `initPage()` is only invoked once, by `app.js::init()` via `window.initPage()`.
  - **#2 (stale `href` closure in `app.js`):** Fixed. `app.js::setupPageTransitions()` line 145 reads `link.getAttribute('href')` at click time, exactly as the doc's proposed fix specifies (not the stale captured `href` variable).
  - **#3 (silent detection failure, `drone-view.js`):** Fixed. `startDetection()` lines 539–542 show the exact guarded toast the doc proposes: `if (!DRONE_STATE.streamUrl || !DRONE_STATE.blockId || !DRONE_STATE.userId) { utils.showToast(...); return; }`.
  - **#4 (orphaned `active` scans on crash, `detection.py`):** Fixed. `_detection_loop()` tracks `completed_normally` and updates the scan to `status: 'failed'` in its `finally` block when the loop didn't finish normally.
  - **#5 (`stopDetection()` not awaited in `handleStreamLost()`):** Fixed. `handleStreamLost()` (line 1012) is `async` and does `await stopDetection()` (line 1020).

## 6. Potential Issues Requiring Runtime Verification

1. **Magnitude of the cross-category double-counting bug (Issue B).** Code tracing proves the defect exists; it does not show how often it actually fires on real footage. **Test needed:** run a real MP4 (or live stream) through the detector twice with identical input, log every `track_id → category` transition inside `detect_frame()`, and count how many distinct `track_id`s appear in more than one category's set by the end of the scan. A nonzero count on typical footage confirms real-world impact and gives a concrete overcount rate.
2. **Actual end-state of Issue A's Firestore write race.** The trace shows the write ordering is deterministic (the `join()` guarantees the background thread's "failed" write happens before `stop_detection()`'s "completed" write), but this has not been observed happening. **Test needed:** start an MP4 upload scan, click "End Scan" partway through analysis (before `manifestReady`), then inspect the resulting `scans/{scanId}` Firestore document directly — confirm it ends at `status: 'completed'`, `manifestReady: true`, and confirm `GET /api/drone/scan/{scanId}/manifest` returns 404 for that ID.
3. **RTSP-vs-HLS capture fallback in production conditions.** `stream_capture.py` prefers RTSP (port 8554) and falls back to HLS only on RTSP open failure, logging a single warning line either way. **Test needed:** run a real DJI Fly session and confirm from server logs which transport is actually used, and confirm detections are actually flowing (not just that the video plays) — a network path that blocks 8554 but allows 8888 would silently fall back and might behave differently (segment-boundary read stalls) without an obviously distinct error.
4. **Coordination between the frontend's 15-second stream-loss timeout and the backend capture thread's independent up-to-5-reconnect retry window.** **Test needed:** briefly interrupt the RTMP publisher (e.g., pause DJI Fly's live stream for 20–30 seconds) and observe whether the frontend declares "Stream lost" while the backend is still mid-reconnect, and what happens to the scan when the backend's `HLSStreamCapture` subsequently does reconnect after the frontend has already called `stopDetection()`.
5. **Model output class names.** `detect_frame()`'s normalization step (lines 351–356) expects `class_name` to be one of a specific small set of string spellings (`bearing`/`Bearing`, `non-bearing`/`non_bearing`/etc.). If `best.pt`'s actual class names (as trained) don't exactly match one of these spellings, every detection of that class silently falls into the `else: print(f"⚠️ Unknown class: {class_name}"); continue` branch (line 357–359) and is dropped entirely — detections would visibly happen (YOLO draws nothing since the track isn't confirmed/counted) but contribute zero to any count. **Test needed:** run one detection pass and check server logs for `⚠️ Unknown class:` lines, or inspect `best.pt`'s `model.names` directly, to confirm the class names match what `detect_frame()` expects.
6. **Concurrent-scan corruption (Issue D) under real conditions.** **Test needed:** open two browser tabs to the same or different blocks, start a live scan in one and an MP4 upload in the other, and confirm whether counts/trackers visibly corrupt each other, as the code trace predicts.
7. **General live end-to-end playback.** No live drone or RTMP publisher was available in this session. Everything about the live path is confirmed by reading code and by the presence of a previously-recorded valid HLS playlist (`output/index.m3u8` + 3 `.ts` segments) on disk — but no live capture → detection → Firestore → UI flow was watched happening in real time.
